## 维护约定

- 同一规则在上表指定的文档中维护，其他文档引用它。正式文档描述当前行为，不能依赖本机计划或会话背景才能使用。
- `local-notes/` 只保存需要长期留存的计划、历史安排、精简操作回执和研究参考；已确认且仍生效的规则须整理进正式文档，并核对代码和验证依据。历史计划中的约束不因存放目录自动失效。
- 一次性执行脚本、工作草稿、下载/传输 ZIP、解压副本和普通临时日志放在 `.build/`。任务结束后，必要测试证据和平台原件分别进入对应归档，`local-notes/operations` 只留下必要结论、限制和归档位置；不重复存放正式证据或把整个工作目录长期保留。恢复必需资料和唯一原件仍按[数据与归档](data-and-archives.md)保护。
- 正式文档不保存历次正文、迁移回执或某次测试通过数。工具版本、格式版本、限制和必要的旧格式兼容说明继续保留。
- 命令、路径、行为或格式改变时，同时更新正文、入口链接及读取这些文档的工具。功能尚未提交时，不单独推送声称该功能已存在的文档。
- `local-notes/` 整根 Git 忽略且受清理保护，需要单独备份。计划名用 `主题-plan-YYYYMMDDTHHmmssZ.md`，操作回执用 `主题-receipt-YYYYMMDDTHHmmssZ.md`，按实际保存时间命名，日期和时间以 `T` 分隔，时区统一为 UTC，末尾 `Z` 标明 UTC；不使用双连字符或修订序号。同主题同一秒需要保留多份时，秒的小数部分以点分隔，毫秒格式为 `HHmmss.fffZ`，禁止覆盖已有文件。历史资料沿用有依据的时间和精度，未知时分秒不补造；文件名时间的依据及被替代关系写入正文或清单。
- 本地索引指出当前有效计划；需要保留的旧版冻结，新修订另存。上游参考资料按来源和版本保存，不作为运行依赖。归档中的离线 README 是随资料携带的使用说明，不能作为第二份独立维护的项目规范。

## 本机资料的准入与核查

`local-notes/` 是经过整理的长期资料目录。草稿、下载、依赖安装、解压目录、可重建中间媒体及普通运行日志先放 `.build/`。任务结束时只转入仍有明确用途的计划、精简回执、研究复核材料或恢复原件；不能把整个工作目录自动登记为长期资料。用户要求保留的计划草稿可以作为有效计划登记，其核定状态写清楚。

目录固定为 `plans/`、`operations/`、`references/`、`history/` 和 `rollback/`；根目录仅保留可维护的 `README.md` 索引和 `retention.json` 保留清单。计划和回执沿用上面的 UTC 命名，回执可为 Markdown 或 JSON。新研究资料包、历史快照和回退包分别用 `references/主题-UTC时间`、`history/主题-UTC时间` 和 `rollback/主题-UTC时间`；研究基准可归入 `references/benchmarks/主题-UTC时间`。按上游版本保留的原件用 `references/upstream/来源/版本`。时间必须是有效日历时间；未知历史时间不补造。

主题和来源使用小写英文字母、数字及单连字符；上游版本标识还允许点和下划线。资料包内部的上游原名和冻结附件名保持来源含义，由精确文件清单管理，不要求给每个附件再加时间戳。

每个独立计划、回执或资料包在本机 `retention.json` 登记以下内容，且根索引必须链接其入口：

- `path`、`kind`、`entrypoint`：相对 `local-notes/` 的独立范围、类型及入口文件；条目范围不得重叠。
- `status`、`reason`、`source`、`timeBasis`：有效状态、长期保留目的、来源及名称时间的实际依据。计划状态为 `active` 或 `historical`，回执/快照为 `historical`，参考资料为 `reference`，恢复包为 `recovery`。历史状态不取消仍生效的约束。
- `retention`：按本条目实际使用的文件角色说明保留理由。角色为 `document`（正文）、`provenance`（来源、身份与迁移依据）、`result`（结果）、`reproduction`（精确复核脚本）、`input`（必要输入）、`upstream`（上游原件）、`diagnostic`（必要诊断）或 `recovery`（恢复必需内容）。
- `files`：逐文件登记相对路径、角色、字节数和小写 SHA-256。不能使用通配符或自动接纳目录里随后出现的文件。发行归档如 wheel/ZIP 还须逐文件写 `reason`，说明保留原件的必要性。

确需复核的精确脚本、固定上游发行原件、输入片段以及解释异常所必需的原始输出可以保留，但须说明用途；普通日志和安装后的运行时不能借此长期存放。依赖目录、Python 缓存、临时残片和可执行运行时会直接被校验拒绝。重跑研究实验时复制材料到 `.build/` 并在那里运行，避免覆盖封存结果。

`retention.json` 的顶层格式为 `{"schema":1,"reviewedAtUtc":"实际审核的UTC时间","entries":[...]}`。清单本身和根索引允许维护；已登记正文和附件按摘要冻结，修订另存。确需迁移时先核对原摘要，保存路径映射与时间依据，再更新索引和保留清单。既有非标准名称使用逐条 `legacyNameReason` 解释，并受 `local-data-policy.json` 中每条历史例外路径的 SHA-256 基线约束；新增文件不能借用历史例外。基线只记录已审核路径的摘要，不把本机文件清单提交 Git，也不要求新工作区或部分恢复拥有全部旧资料。

```powershell
npm run notes:check
npm run notes:inventory -- --path references/主题-UTC时间
npm run test:notes
```

`notes:inventory` 只读输出指定范围的路径、长度及摘要，用于人工审阅后编写条目，不写清单、不自动批准保留。`notes:check` 直接扫描被 Git 忽略的实际目录，核对命名、用途字段、精确文件范围、索引、摘要、依赖缓存和目录链接。未登记文件、空目录、缺失附件及被修改的原件均导致失败；不能直接批量刷新摘要来消除错误。文件系统仍允许手工写入，检查用于任务收尾和后续入口把关，不是文件写入拦截器，也不判断研究结论本身是否正确。

存在本机笔记的任务在结束前执行 `notes:check`；正式测试入口在建立源码快照前执行同一检查，`local-data.ps1 -Action Verify` 也执行。没有该目录的全新克隆正常通过；有目录却缺少索引或保留清单时失败。校验器及其回归测试随源码维护，实际笔记、清单和迁移回执仍全部被 Git 忽略并需独立备份。目录继续受清理保护，核查失败不触发自动删除或自动过期。
