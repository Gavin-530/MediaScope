# 贡献与提交规范

项目采用 Conventional Commits 结构。对应代码、测试和必要文档按同一逻辑目的交付，独立的功能、CI、归档和发布准备分别提交。

## 提交说明

```text
type(scope): describe the concrete change
```

标题最多 72 个 Unicode 字符，不带末尾句号。类型和范围使用小写；范围可省略，允许字母、数字和 `-`、`/`、`.` 分隔，例如 `report`、`test/server`。中英文均可，英文优先沿用项目风格、使用动词原形。描述应能由差异核对，避免只写“优化”“完善”“update”。

| 类型 | 用途 |
| --- | --- |
| `feat` / `fix` | 增加功能 / 修正行为，界面和文案按实际目的分类 |
| `perf` / `refactor` | 有测量依据的性能改善 / 不改变功能的结构调整 |
| `test` / `docs` | 测试 / 文档和注释 |
| `style` | 仅代码排版等不改变含义的变化 |
| `ci` / `build` | 工作流 / 构建、打包和依赖 |
| `chore` / `revert` | 其他维护（发布准备为 `chore(release)`）/ 撤销改动 |

简单改动可省略正文；复杂改动在标题后空一行，说明问题、结果、实现选择及兼容或迁移影响。正文建议约 72 列换行，URL 和代码标识可保持完整。不兼容变化须有 `BREAKING CHANGE: <影响和迁移办法>`；即使标题使用 `!` 也须填写。只在有真实关联时填写 `Fixes:`、`Refs:` 和 `Co-authored-by:`。

`chore(release)` 标题中的版本须与该提交的 `package.json` 一致；存在锁文件时，顶层和根包版本也须一致。撤回和纠正关系写入正文，版本选择遵循[发布规范](releasing.md)。

真正有多个父提交的自动 `Merge ...` 标题允许保留；普通提交不能借此绕过检查。`git revert` 自动标题及引用完整 SHA 的撤销正文允许保留。

## 分支选择与交付范围

本节完整通用回归要求对符合[文档轻量准入](testing.md#ci-文档轻量检查)的纯说明性文档 push 允许轻量替代。已切换[分工验收](testing.md#本地与-actions-分工验收)的 `main` 直推使用同 SHA 预检和独立必需检查。提交说明、最终差异审阅和服务器必需检查均须通过。发布按发布规范执行，PR 和合并队列继续提供原全量检查。

`main` 是日常开发、集成和交付的默认主线。新交付先用获准的候选分支或预检标签验证最终 SHA，提交说明、应跑通用范围及必要专项检查均通过后才能进入主线。范围明确、可独立回退的小改动不要求额外审批或创建 PR；仍须先验证再更新主线。是否需要 PR 和集中审阅按实际影响判断，不按文件数、扩展名或提交类型机械分类。分支授权以 [AGENTS.md](../AGENTS.md) 为准。

| 分类 | 判断条件 | 默认交付流程 |
| --- | --- | --- |
| 日常小范围完善 | 已定位的局部缺陷修复、局部功能或界面完善、测试补充、文档修正；影响边界清楚，不改变关键兼容约定或数据安全，能通过针对性检查并独立回退 | 在短期候选分支完成本地针对性检查和最终 SHA 的云端检查，再快进交付 `main`；不要求额外审批或创建 PR |
| 重要改造或实验 | 涉及测量定义、核心算法或格式兼容的实质调整，改变删除/权限等安全边界、关键验收门槛，或存在跨模块改造、实验方案未定、需集中验证等情况 | 使用一个短期主题分支完成该项工作，经相应验证和审阅后合入 `main` |
| 并行或影响不明的工作 | 多项工作需隔离、变更尚不能证明可安全独立交付，或需他人审阅后才能判断 | 使用与该项工作对应的分支，明确待确认事项；确认边界和验证要求后再合入 |

候选分支用于让必要检查在主线接收前完成，不表示每项小改动都需要额外审批。小改动触及关键数值、兼容或数据安全时仍须按实际后果增加审阅和专项验证。已经充分验证的重要工作也可以由维护者明确选择以同一 SHA 快进交付主线，但不能省略候选验证。

不经 PR 快进推送须同时满足：远端允许该操作；已核对最新远端 `main` 与本地历史，没有覆盖他人提交；暂存区只含本次范围；已完成提交说明、差异及受影响的功能检查，文档同时核对链接；候选分支上最终 SHA 的 `Commit messages`、`Windows full regression` 及其他适用检查全部完成且合格，没有与本次改动有关的未解释失败。不得把尚无云端检查的新 SHA 首次直接推入 `main`。使用普通快进推送，远端前进导致拒绝时重新核对和整合，不强推。推送后核对远端实际 SHA，并跟进该 SHA 触发的检查；推送成功不能写成验证通过。

维护者明确选择将重要改动不经 PR 快进交付主线时，须说明原因，并在推送前完成候选验证、最终差异审阅和可行的回退准备。尚缺必要验证、无法核对远端身份或服务器要求 PR 时，继续在分支补齐条件；不为简化交付省略验证。紧急修复也须保持这些身份、验证和记录要求；确实无法完成时如实报告缺口，不宣称已通过。

“本地提交”“推送到远端分支”“合入 `main`”“发布版本”分别说明。日常小改动只要求“提交到 GitHub”时，默认目标为 `main`；需要先走分支时说明具体原因及交付目标，不擅自把推送分支表述为主线已更新。任务目标是更新 `main` 时，在检查条件和授权范围内完成主线交付，不能只推一个中间分支就宣称完成。已明确指定目标和操作的要求不重复询问；服务器保护和验证条件仍须满足。代码提交不等于发布版本。

## 主题分支命名

需要主题分支时，统一采用 `<type>/<topic>`。`type` 表示整项工作的主要目的，采用上文提交类型；另设 `experiment`，用于方法或可行性尚待验证的实验。`topic` 使用简短、具体的小写英文单词或数字，单词之间用单连字符连接。

| 工作目的 | 名称示例 |
| --- | --- |
| 新增功能 | `feat/repeat-frame-analysis` |
| 修复缺陷 | `fix/report-export` |
| 重构 | `refactor/report-parser` |
| 文档 | `docs/development-guide` |
| 构建、依赖 | `build/update-dependencies` |
| 一般维护 | `chore/archive-maintenance` |
| 实验验证 | `experiment/frame-fingerprint` |

一个分支对应一项可独立审阅的工作，可以连续提交功能、测试和文档；各提交按实际内容选择自己的类型。分支名称中的类型用于说明工作目的，验证、合入和发布仍分别遵循本文件、[测试规范](testing.md)及[发布规范](releasing.md)。

创建前执行 `git check-ref-format --branch <name>` 核对语法，并检查本地、远端是否存在同名分支或路径层级冲突。改名时核对关联工作区、上游和未提交修改；已推送分支还须核对开放 PR、保护规则及工作流引用。完成后核对提交 SHA、分支引用及工作文件，确认改名结果和关联设置符合预期。

此命名形式是本项目的协作约定。名称语法依据 [Git 引用名称规则](https://git-scm.com/docs/git-check-ref-format)，简短、描述性的命名参考 [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)；上文提交类型参考 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。

## 提交前核对

1. 核对远端仓库、最新 `main`、当前分支、已有暂存内容、未提交编辑及作者身份。无关编辑保留，不为切分支而自动丢弃、重置或提交；按明确路径或分块暂存，提交前复核实际暂存差异。
2. 从核对过的 `main` 基线创建或更新候选分支，一项独立工作使用一个短期分支，可在其中连续提交和修正，不按文件或提交次数新建分支。已有相关分支可继续使用；无关工作单独交付，不顺带放入正在审阅的 PR。
3. 完成与本次影响相符的本地检查，并将代码、测试和必要正式文档一起审阅。纯文字修正检查差异、格式和链接；功能改动按[测试规范](testing.md)执行受影响检查。首次推送候选前完成这些检查，避免把云端回归当作可以省略本地相关验证的理由。完整通用回归由 Actions 承担，不要求本地机械重复同一套通用回归。专项验证和发布验收仍按各自范围执行。
4. 核对本人稳定署名和关联 GitHub 账号的邮箱（可用官方 noreply 地址）。保留他人原作者身份，不代填推测信息。私有笔记、测试缓存、用户资料及发行附件的提交边界按[数据与归档](data-and-archives.md#源码软件和对外资料边界)核对。

## PR 审阅与主分支合入

使用[PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)，标题遵循提交标题规则，正文说明问题、结果、风险分类、兼容性及实际验证。提交检查器只核对格式；维护者还须审阅最终差异和证据。单人维护可以自行完成这项审阅，但不能把自查称为独立同行审阅；GitHub 另有审批要求时仍须满足。

合入前必须核对：

- PR 的目标确为预期 `main`，最终 head、base 与已审阅范围一致；发生冲突、追加修改或基线更新时重新审阅受影响部分，补齐未被原检查覆盖的验证。
- 当前合并候选所需的提交说明检查、完整通用回归及其他适用检查已完成，结果符合[测试规范](testing.md)。相关检查排队、运行、失败、取消、缺失或证据不完整时，不声明合入条件已满足；重试不抹去原失败，须说明原因和解决依据。
- 检查的实际源码、测试 SHA、验证器和范围与候选对应，不能用旧提交、含额外本地编辑的结果或部分套件冒充当前完整验证。GitHub 状态图标本身不能替代正式记录的计数、范围和完整性。
- 未解决的阻塞审阅意见、冲突及服务器要求已处理；实际具备合并授权。同一逻辑目的的临时尝试和连续修正应在尚未合并的分支上整理，多条独立完整提交可保留。整理须先于最终 SHA 验证；核对最终提交说明、贡献者和所选合并方式。

合并后核对远端 `main` 的实际 SHA、必要改动是否已包含及新触发的检查。PR head、PR 测试合并 SHA 与最终 squash/rebase/merge 提交可能不同，不能把前一个 SHA 的通过直接记成后一个 SHA 的验证；发布仍须满足[发布规范](releasing.md)对确切提交和附件的要求。交付说明写明提交、目标分支、PR/合并状态和检查结果；未完成项明确列出。

需要主线接收前验证确切提交时，先在候选分支完成整理和必要的合并，验证最终 SHA，再将同一 SHA 快进交付主线。不要在验证后才 squash、rebase 或添加修改；这些操作产生新 SHA 时重新满足检查条件。候选失败应保存原因及修复依据，后续绿色结果不改变旧运行的真实结论。

主题分支结束后，确认必要提交已纳入主线、没有待保留的独有改动且无其他使用者，再删除该分支；本地未提交编辑仍须保留。日常历史整理限于尚未合并的功能分支，共享分支须协调。主线出现问题时通常追加修复或 `git revert`，记录原因并重新验证。只有经仓库所有者明确授权且通过[主线历史恢复验收](testing.md#主线历史恢复验收)的指定更新才可改写 `main`；已发布标签和封存证据不随之改写，失败记录须保留。

## 项目要求与 GitHub 保护

以上是项目操作要求，文档修改不会自动配置 GitHub。`main` 须配置 `Commit messages` 和当前回归门禁为必需检查。切换前使用 `Windows full regression`，切换后使用 `MediaScope split acceptance`。必需检查限定预期 GitHub Actions 来源，禁止删除，普通交付禁止强推，规则应用于管理员。只有服务器能够将非快进权限单独授予恢复身份、同时继续强制全部必需检查及其他适用保护时，才可启用恢复。服务器是否另行强制 PR、审批或其他条件，以实际配置为准；单人维护不伪称独立同行审批。若服务器要求所有变更走 PR，上述不经 PR 快进选项也不适用。不得为一次提交临时关闭保护、移除必要测试或利用绕过权限制造通过。配置无法生效时明确报告服务器未强制的缺口，不把文档要求说成已经配置完成。

主线门禁约束接收时的候选状态，不保证以后重新运行永不失败。GitHub 可接受的状态不完全等于项目测试门槛；完整通用回归仍须核对非零用例、零失败/取消/跳过/TODO 和功能映射，不单凭绿色图标放行。

流程参考 [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)，服务器能力参见 [GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。本项目的风险分类、验证和发布门槛以本文件及所链接的正式规范为准，不把通用流程介绍当作所有仓库统一强制的标准。

## 检查入口

```powershell
npm run check:commits
npm run check:commits -- --range HEAD~1..HEAD
node scripts/check-commits.mjs --file <UTF-8提交说明文件>
npm run test:commits
```

默认检查基线 `fc648355fcc12e1a07003fd75746cedf8a73bdba` 之后的提交；该基线及其祖先（36 条）按确切 SHA 豁免，旧分支新增提交不豁免。`--file` 只检查说明格式，不验证尚未创建的提交版本。退出码 `0` 为检查通过（可能没有新提交），`1` 为不合格，`2` 为参数、事件或 Git 对象缺失；浅克隆须补齐所需历史。

普通 push 检查事件的 `before..after` 范围；新建分支和 GitHub 明确标记 `forced: true` 的 push 检查固定基线之后的全部目标历史。强推前的旧提交可能已不在新克隆中，不能依赖它确定范围；完整历史检查仍逐项验证提交，豁免边界保持不变。其他事件或所需基线/目标对象缺失时继续以退出码 `2` 阻塞，不把缺失当作通过。事件标记依据 [GitHub push 事件定义](https://docs.github.com/en/webhooks/webhook-events-and-payloads#push)。

[Commit messages 工作流](../.github/workflows/commit-messages.yml) 在推送、PR、合并队列和手动执行时检查新增提交，PR 另检查标题。它读取事件 JSON，不把标题插入 shell。修改推送后才生效，管理员还须配置必需分支检查；格式检查不运行产品回归，也不自动发布。
