# 发布规范

## 版本与附件

| 对象 | 命名 |
| --- | --- |
| 软件版本 | 与 `package.json` 一致；预发布为 `-alpha`、`-beta`、`-rc`，可附 `.数字` |
| Git Tag | `v<版本>`，指向确切验收的发布提交；软件包须有实际构建或符合下述条件的复用记录 |
| Release 标题 | `MediaScope <版本>` |
| Windows ZIP | `MediaScope-<版本>-win-x64.zip`，包内版本与附件名不加 `v` |

修复递增补丁号，兼容功能新增递增次版本号。不兼容变化在 `0.x` 阶段递增次版本号，`1.0.0` 起递增主版本号。预发布在 GitHub 标记为预发布。版本按实际发布范围确定，不仅凭提交类型自动改号。已发布版本的附件不可替换，新字节须用新版本。尚未发布的候选可在同一版本下重建，但须先核对平台状态、保留旧包及证据，在独立工作区输出新包并记录其替代关系；不得覆盖旧包、沿用旧摘要或冒用旧验收。最终发布仍须固定并验收新提交与新附件；标签调整按贡献规范办理，不因重建自动移动。

## 发布步骤

1. 按[贡献规范](contributing.md)提交对应代码、测试和文档，运行 `npm run check:commits`，核对版本、提交及 Tag。版本号相同不能证明源码相同。
   先完成候选提交整理，再固定发布 SHA；验证后追加修改、squash、rebase 或改变合并结果时，须重新核对新 SHA 的验收。提交历史调整不会自动改变 ZIP 内容，但旧 SHA 的通过不能替代新 SHA 的来源验收。
2. 对确切发布 SHA 完成分工验收：Actions 运行 `npm run test:release` 的完整通用回归，本地干净工作区运行 `npm run test:gpu:release` 的真实 GPU 验收；本地不强制重复完整通用回归。导入或下载云端独立记录后，执行 `npm run test:acceptance -- <通用记录目录> <GPU记录目录> <发布SHA>`，校验两类记录完整性及相同源码/验证器身份。GPU 不可用、CPU 回退、任何失败/取消/跳过/TODO、不完整覆盖或归档阻塞均不能满足对应验收。日常部分检查不能替代上述范围。
3. 首次构建执行 `scripts/package.ps1 -Version <版本>`，生成一个 Windows x64 联网部署 ZIP；符合下述逐项输入核对条件的已有 ZIP 可复用，并继续完成附件验收。已有包及暂存目录不覆盖。构建机使用系统 .NET Framework 4 x64 编译器生成应用启动器，临时文件留在当前工作区 `.build`，不下载编译工具；编译失败须修复后重新打包。启动器、引导脚本和构建摘要纳入包清单。发行校验只允许摘要与构建记录一致的 `scripts/MediaScope.Launcher.exe`，其他 EXE/DLL 仍不得入包，Node.js/FFmpeg 仍按运行时清单安装。
4. 对确切附件执行下列离线及真实首次联网部署检查，核对 ZIP 摘要、字节数和结构化断言；另在锁定私有环境下验证应用。离线运输夹具不能证明联网下载通过。

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/record-test.ps1 -Kind Package -Archive <zip> -RequireClean
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/record-test.ps1 -Kind OnlineDeployment -Archive <zip> -RequireClean
   ```

5. 完成人工验收和兼容性核对，保存实际结果和未验证范围。按[源码、软件和对外资料边界](data-and-archives.md#源码软件和对外资料边界)核对提交范围及实际附件；私有研究记录不得直接当作公开附件上传。
6. 使用[Release 模板](../.github/RELEASE_TEMPLATE.md)审查草稿并执行下述正文检查。草稿可提前准备，但不代表已满足发布条件。核对最新目标分支、冲突、必需检查与审批，以及确切发布 SHA 的通用回归和 GPU 记录。同一 SHA 的已完成合格通用记录可供 Tag 复用，不要求标签再次跑全套；没有记录则对该 Tag 手动触发 Actions。PR 合并测试 SHA 与发布 SHA 不同则不能替代。等待所有已触发的相关检查结束并解释已有失败，不能通过停用触发器、移走用例或只选绿色记录放行。分别核对通用、GPU、附件部署与人工验收的覆盖及限制，不能用正文检查替代这些验收。
7. 上传附件后下载实际附件，与本地已验收附件逐项核对名称、字节数和摘要；用下载的附件再次执行正文检查，确认附件清单完整后再发布 Release。说明如实注明推荐环境首次安装需要联网。发布后显式同步平台资料，云端限期产物及时下载并校验；方法见[数据与归档](data-and-archives.md)。

自动部署检查覆盖环境复用/变化检测、切回推荐环境、升级/回退、下载损坏、兼容失败、用户数据、自定义安装位置、共享组件及卸载边界。人工至少检查首次位置选择/取消、可用环境的双选项弹窗、未自动找到合格环境时手动选择组件/下载/取消、同目录 FFprobe 自动识别及缺失时单独选择、手动组件验证失败后的确认/拒绝、环境失效后的确认/拒绝，以及 Windows 卸载并保留报告。每版核对旧报告/配置、升级方式、环境要求和实际已知问题；未执行项不得写为通过。

已有 ZIP 只有在逐项确认打包清单内的源文件、打包脚本、启动器源文件和构建输入、运行时锁定清单全部相同后，才可复用于相同软件版本的另一个源码提交。另存对应关系记录，列明原构建/核对提交、新提交、包摘要、输入比较及新 SHA 的实际验收；不得改写原构建记录或封存证据，也不得将复用表述为重新构建。包内字节变化时不能复用；按上文区分未发布候选重建和已发布版本递增，均不覆盖原包。此规则不授权移动已发布标签或重写共享历史。

## 发布正文

- 正文仅有两个标题，依次为 `## 本次更新`、`## 校验`，不增加其他级别或分类标题，正文从“本次更新”开始。规则约束结构，不限制必要说明的长度或条目数量，不要求凑齐变化类型。
- “本次更新”仅列相对此前实际发布版本的重要变化，使用一层列表说明具体改动及用户影响，不设置分类配额。先写必要操作和重要兼容影响，再按用户影响排列主要功能与修复。未变化的功能和默认行为留在使用文档，不因本轮核查而补成更新条目。复杂说明链接对应版本文档，必要条件和限制仍须写清。
- 每项描述须能由两端版本差异、实现或实际验证记录核对；写“调整”“改善”等变化时须说明具体行为，不使用无依据的性能、精度、兼容或质量结论。同一事实只写一次，不重复标题、功能介绍和验证说明；发布正文不承担操作回执或完整功能手册的职责。
- 兼容、升级和已知问题有实际内容时，使用“注意：”“兼容性：”“已知问题：”等段落或列表项说明，不另设标题，不重复同一事实，不填“无”。每版都须核对这些事项，未验证不能宣称完全兼容、无已知问题或全面测试通过。固定安装、启动和环境说明引用对应版本的 [README](../README.md)，本版改变的要求及首次推荐环境需要联网仍须明确说明。
- 正文以产品变化、使用要求和影响发布状态的限制为主；外部贡献注明真实贡献者和 PR。验证摘要按需链接对应 Actions；逐次测试计数、重试经过、本机工具故障、归档和历史整理流水留在正式证据及内部回执，不作为产品更新条目。比较链接使用核对过的 Tag，自动生成的 PR 列表不能替代版本差异审阅。
- “校验”固定使用一个 `text` 围栏代码块，每个实际发布 ZIP 一行：`<64位小写SHA-256><两个空格><准确附件文件名>`。列出整个 ZIP 的摘要，不使用包内单文件摘要；全部附件与正文清单一一对应。必要的校验方法可用普通段落说明，不增加标题。摘要证明文件一致性，不证明功能正确或验收通过。
- 发布前移除提示、占位符和空内容，按下述入口检查正文结构与本地附件；工具不验证产品描述、链接目标、版本差异完整性或发布验收，也不自动读取 GitHub 附件清单，这些仍须审阅。已发布正文可修正排版、链接、笔误或精简重复表述，编辑前保留平台正文快照，不改变产品事实、适用边界和发布状态；历史补录明确标注，不补造验收结论。新规则适用于后续发布和本次待发布草稿，不据此自动改写历史 Release。

```powershell
node scripts/check-release-notes.mjs --body <UTF-8正文文件> --archive <ZIP路径>
```

多个 ZIP 重复传入 `--archive`，必须列出全部拟上传附件；上传后以全部实际下载附件复查。非 ZIP 附件尚无发布约定，需要时先扩展规则和检查器，不能漏报。正文草稿、下载副本及检查输出放在当前工作区 `.build/`；Release 标题、Tag 和发布状态另行核对。退出码 `0` 只表示结构与所给文件的名称/摘要一致，`1` 为不符合规则，`2` 为参数或文件读取错误。

本地档案、归档工具和文档整理不会自动发布软件，正式包继续单独保存在 `releases/`。
